# 把新指正继续提炼成判断方法

本包保存了一个作者的已记录经验。同事使用时，当前项目的要求和反馈继续有效；不把新项目偏好自动推广给所有人。

## 一条反馈要保存什么

当用户要求记住、任务需要连续迭代或项目已采用反馈记录时，写入项目内可访问的记录。使用现有记录格式；没有格式时可记以下字段，不强迫简单修改填全表。

| 字段 | 用途 |
| --- | --- |
| 当前任务与基准版本 | 识别是在什么事实、参考和认可结果上修改 |
| 反馈原意 | 简短准确转述用户指出的问题，避免替用户补动机 |
| 失败现象与维度 | 例如反打仍见原墙、楼梯落在墙面、规模与用途不符、面部不可读 |
| 判断依据 | 剧本、可见图像、用户明确偏好或尚待验证的推断 |
| 根因与修改动作 | 错在世界位置、遮挡、容量、光源还是旧词冲突；具体怎样改 |
| 必须保留 | 被认可的身份、主意象、体量、布局、材质等 |
| 范围与例外 | 当前镜头、当前项目、相同任务类别或可推广原则 |
| 结果与状态 | 用户明确认可、否定、局部认可、未回复或待图像验证 |
| 来源和更新日期 | 可以追溯原记录并识别后来改变的结论 |

只有用户明确认可才记为用户认可；沉默、生成完成、文字合规和自动检查通过都不是验收。局部认可必须指出维度，不能把整张图或整种风格一起升级。

## 怎样从纠错得到通用方法

1. 先保存本次具体纠错，不立即把它变成永久限制。
2. 比较其他任务：共同的失败机制是否相同？如果只是某个角色、房间、配色或表格格式，留在项目层。
3. 能推广时写成“适用条件 → 判断依据 → 动作 → 保留项 → 失败边界”。将用户已说的理由与自己的解释区分。
4. 有冲突先找有效范围和时间：当前明确选择取代同范围旧选择；不同项目的相反选择可以同时保留。旧方案记为废弃或反例，不能与现行方案一起拼进提示词。
5. 在新的同类任务上检查是否减少原错误。尚未测试的新规则标为候选，不以归档次数证明有效。

## 多人共享的更新

个人工作记录可以持续累积。共享包的更新需要明确提出修改请求或已有团队维护授权，再由维护者核对证据、去重和范围。先修正狭窄根因，避免每次失败就增添一个通用禁令。

共享版本至少记录修改内容、来源范围和版本。项目特有的名字、机密剧情、原图与账户信息不进入通用包；可用去标识的失败机制与修正摘要替代。

跨对话能够继续使用的是实际保存并可访问的文件。没有写入记录时，不承诺未来对话必定保留本次意见。
